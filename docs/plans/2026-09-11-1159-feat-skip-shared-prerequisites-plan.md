# Skip Shared Prerequisites - Plan

## Goal Capsule

- **Objective:** Build, once, the two pieces of infrastructure three of the four Skip/Convex spikes (1a, 1b, Direction 2) are hard-blocked on and independently defer to "planning" — a documented atomic multi-table write convention for Skip, and a correctness-comparator plus fault-injection harness — as two independently reviewable, independently useful deliverables, so none of the three re-solves either and none of their correctness claims rests on ungrounded ad hoc code. The fourth spike, 1c, already designed its own equivalent of both (KTD7-KTD9; `bench/compare.ts`/KTD10) before either existed as a shared artifact — for 1c this plan is a beneficial reuse opportunity, not a blocking dependency (see Problem Frame and Key Decisions for the classification, and How This Work Fits Together for the per-spike detail).
- **Means:** (P) Extract and formalize the tagged-envelope pattern already proven in `~/src/skip/examples/convex_reactive` into a documented convention and a small reusable TypeScript library. (Q) Build a shared correctness-comparator and fault-injection harness against the PoC vehicle already frozen by research (`~/src/convex-tutorial`'s `messages`/`users` tables plus aggregates A1/A2), exposing counters and timers matching the shared catalog research already defined.
- **Product authority:** Not separately brainstormed — derived directly from four already product-authority-settled sibling plans. Three (1a, 1b, Direction 2) explicitly defer the same two structural problems to their own planning under different requirement numbers, each still carrying the underlying design question as an unresolved Outstanding Question (see Problem Frame). The fourth (1c) already solved its own version and is not blocked. This plan owns the shared prerequisite tier beneath 1a/1b/Direction 2, plus a beneficial-reuse relationship with 1c; see How This Work Fits Together for the exact per-spike mapping.
- **Open blockers:** None at product scope. Planning must choose a packaging location for the P library (a new directory under `npm-packages/` in this repo vs. a contribution to `~/src/skip/examples/` or `skipruntime-ts/adapters/`) and a process topology for the Q harness (in-process test helper vs. a small standalone server).

## Product Contract

### Summary

A foundational, fifth plan alongside the four Skip/Convex integration spikes (1a, 1b, 1c, Direction 2). It builds no spike itself. It extracts the already-proven tagged-envelope atomic-write convention from `~/src/skip/examples/convex_reactive` into a reusable TypeScript library (P), and it builds the correctness-comparator and fault-injection harness that none of the four spikes currently has (Q), wired to the PoC vehicle research already froze: `~/src/convex-tutorial`'s `messages`/`users` tables and the A1 (per-user reducer count) and A2 (joined latest-N feed) aggregates. Both sub-deliverables are reviewable on their own terms, independent of which (if any) spike is later generalized to production.

### Problem Frame

Three of the four sibling plans (1a, 1b, Direction 2) independently state the same two open items and defer both to their own planning as unresolved Outstanding Questions, using different requirement numbers for what is structurally one problem in each case — that combination (`requirements-only` status, plus the gap still open in the plan's own text) is what makes this a hard prerequisite rather than a shared concern. The fourth plan, 1c, already designed and documents its own solution to both; its relationship to this plan is reuse, not blocking — see the "not hard-blocked" paragraphs below and the Reconciliation subsection under How This Work Fits Together.

**(a) Atomic multi-collection update — hard prerequisite for 1a, 1b, and Direction 2.** Skip Runtime's public TypeScript API has no batch-write primitive: `CollectionWriter.update` (`~/src/skip` `skipruntime-ts/core/src/index.ts:476-501`) forks, writes, and merges one collection per call; `ServiceInstance.update` (`:768-782`) is equally single-collection; no `updateMany` exists anywhere in skipruntime-ts or skiplang (confirmed by exhaustive grep, not in the CHANGELOG through v0.0.19 — `research/skip-convex-integration/research-skip-atomic-write.md`). All three plans are still `requirements-only`, none has designed a solution of its own, and each still carries this as an open, undecided Outstanding Question, not merely a stated concern:
- 1a (`docs/plans/2026-09-10-1509-feat-skip-sync-protocol-client-plan.md`) R2 requires "each fully reassembled `Transition`... applied to Skip as one atomic update." Its Dependencies/Assumptions section states plainly: "Skip Runtime's public TypeScript API does not currently expose one atomic write spanning several external collections. Planning must satisfy R2..." (line 188), and its Outstanding Questions repeats it unresolved: "Whether one combined Skip input domain or a scoped multi-collection atomic update is the smaller way to satisfy R2" (line 196).
- 1b (`docs/plans/2026-09-10-1843-feat-skip-paginated-reactive-source-spike-plan.md`) R4 requires that when a page splits, "old and new page regions are exchanged in one atomic Skip update." Its Dependencies/Assumptions states the identical structural gap in page-swap terms: "Atomic replacement of one page with two requires either a combined tagged Skip input domain or a narrowly scoped multi-region atomic update mechanism" (line 193), and its Outstanding Questions leaves it open: "Which combined-domain or atomic multi-region representation satisfies R4 with the least Skip Runtime change?" (line 202).
- Direction 2 (`docs/plans/2026-09-10-1702-feat-skip-incremental-materialized-cache-spike-plan.md`) R2 requires "all source changes from one Convex transaction become visible to the materialized view atomically at one Convex commit version." Its Dependencies/Assumptions states it almost verbatim to 1a's: "Skip Runtime's current public TypeScript update surface does not expose one atomic write spanning multiple external collections. The spike must use one combined input domain or add a narrowly scoped atomic update capability without weakening R2" (line 236), and its Outstanding Questions leaves the same choice open: "Will one combined Skip input domain or a scoped multi-collection atomic update mechanism satisfy R2 with less risk?" (line 247).

All three restate the identical undecided design question in their own words. `research-skip-source-state.md`'s "Combined input (atomicity without a runtime change)" section already resolves it, generalizing the pattern proven in `~/src/skip/examples/convex_reactive/skip/service.ts`: that example's Convex query returns a tagged union `WorkspaceRow` (`shared/model.ts:16-18`, `kind: "project" | "task"`) delivered as one `callbacks.update` per Transition, then split downstream via `ProjectsOnly`/`TasksOnly` mappers (`service.ts:34-49`) and rejoined via `TasksByProject`/`AddTaskTotals`/`AttachTotals` (`:51-89,160-161`). `DESIGN.md:114-118` names exactly why: "Separate subscriptions would each be consistent inside Convex, but their callbacks could enter Skip separately... One combined query result is diffed and delivered through one `callbacks.update` call." `DESIGN.md:314-315` names the hazard this avoids for any future partitioning: "N partitions are N independent subscriptions delivering into Skip separately." No Skip runtime change is needed — the fix is a convention plus a small library, not new FFI.

**1c is not hard-blocked on this.** 1c (`docs/plans/2026-09-10-1854-feat-skip-data-sync-push-source-spike-plan.md`) R8 requires the consumer to group page values "by exact Convex revision timestamp and apply every upsert, tombstone, and freshness-control change from one transaction to Skip atomically before publishing derived effects" — the same structural requirement — but as of 2026-09-11, 1c is `implementation-ready` (not yet built — no code exists, only its plan document) and has already fully designed its own version: KTD7 ("Model ingestion as a generation-fenced state machine"), KTD8 ("Put documents and source-control metadata in one Skip collection... One `callbacks.update` call can therefore apply both tables and freshness state atomically"), and KTD9 (generation-scoped replay watermarks and a pending-page ledger) — a strict superset of the simpler `convex_reactive` pattern above. 1c's relationship to this plan's P deliverable is a beneficial reuse opportunity, not a blocking dependency.

**(b) Correctness-comparator harness — hard prerequisite for 1a, 1b, and Direction 2.** Each plan's acceptance bar is phrased differently but is structurally the same requirement: Skip's output must match an independent, separately-executed native Convex query at a settled checkpoint. As with (a), these three plans have no comparator design of their own:
- 1a R6: "the demo's Skip-derived aggregate matches an independent Convex reader" at controlled checkpoints across six named scenarios.
- 1b R9/R13: the feed and aggregate must "match an independent monolithic indexed Convex query" at settled checkpoints, and the report "compares the paginated source with a monolithic indexed query."
- Direction 2's correctness section (R13): "Correctness is checked against an independent native Convex result for the same logical commit version" across seven named scenarios.

`research-poc-vehicle-and-harness.md` states plainly: "No harness exists" (line 76). A grep across this repo confirms it: `crates/common/src/comparators/` (`lower_bound.rs`, `tuple.rs`, `mod.rs`) is an unrelated query-engine comparator with no relation to Skip or cross-system correctness checking, and no comparator/fault-injection code exists anywhere else in `convex-backend`. `~/src/convex-tutorial/convex/chat.test.ts` has real `convex-test`/vitest infrastructure (e.g. `getOrCreateUser` idempotency test) that can serve as half of the independent-native-reader path, but the comparator, settled-checkpoint anchoring, and fault-injection layer do not exist for any of 1a, 1b, or Direction 2. Building this once, against the vehicle `research-poc-vehicle-and-harness.md` already froze, removes a duplicated build for these three and gives each spike's correctness claim the same ground truth.

**1c is not hard-blocked on this either.** 1c R15: "A comparison harness drives deterministic writes, pauses writes at settled checkpoints, and compares the current Skip result with an independent native Convex query," covering eight named fault scenarios — but 1c already designed its own comparator (`bench/compare.ts`, KTD10's JSONL schema) as part of its 2026-09-11 implementation-ready deepening. 1c's relationship to this plan's Q deliverable is the same beneficial-reuse pattern as P's — see Reconciliation below.

Both gaps are phrased independently by session-isolated planning passes on each spike, using different requirement vocabularies, over the same two missing pieces of infrastructure — this is real duplication, not a coincidence of terminology. For 1a, 1b, and Direction 2 it is a genuine blocker: none of R2(1a)/R4(1b)/R2(Dir2) or R6(1a)/R9,R13(1b)/R13(Dir2) can be satisfied by that spike's own planning without either re-deriving the envelope convention or re-building a comparator from scratch. 1c's R8 and R15 describe the same structural requirements, but 1c already re-derived both independently and in more advanced form (KTD7-KTD9; `bench/compare.ts`/KTD10) before this plan existed, so 1c's version of the duplication is a completed, working re-derivation rather than an open blocker — this plan's value to 1c is consolidation and reuse, not unblocking.

### Key Decisions

- **One combined plan document, two independently implementable sub-plans, not a merged requirement list and not two separate documents.** (Governs document structure.) The two sub-deliverables have different plausible implementers — P touches TypeScript and Skip's mapper/reducer API, Q touches the PoC vehicle app plus a Node/TS test harness — and different review boundaries, so they get their own requirement-ID prefixes (`P1-Pn`, `Q1-Qn`). They stay in one document because they share the same PoC vehicle (`~/src/convex-tutorial`) and the same relationship to all four downstream spikes, and both must land before any of 1a/1b/1c/Direction 2 can be implemented and evaluated for real; splitting into two documents would duplicate the vehicle-freezing content and the four-spike relationship mapping.
- **P and Q are hard prerequisites for 1a, 1b, and Direction 2; beneficial reuse only for 1c.** (Governs Problem Frame, How This Work Fits Together, Success Criteria.) 1a, 1b, and Direction 2 are all `requirements-only` and each still lists the identical atomic-write and comparator gaps as open, undecided Outstanding Questions in its own text — none has a design of its own to fall back on, which is what makes P and Q genuinely blocking for these three. 1c is `implementation-ready` and already designed its own equivalent of both (KTD7-KTD9; `bench/compare.ts`/KTD10); for 1c this plan is a consolidation/reuse opportunity, not something 1c is blocked without.
- **Extract and formalize, don't invent — for P1-P8.** The envelope convention is already shipped and working in `~/src/skip/examples/convex_reactive`; P1-P8's job is documentation plus a small reusable library around an existing, working pattern, not new design risk. **P9 is the exception:** its generation-fencing and replay-ledger scope has no shipped precedent in `convex_reactive` and follows 1c's KTD7-KTD9 design instead, which 1c's own plan flags as resting on Skip `ExternalService` capabilities unverified against Skip's source. P9 carries real, not-yet-retired design risk that P1-P8 do not.
- **Build the harness once, against the vehicle research already froze, reused unmodified by all four spikes.** (Governs Q1-Q10.) `research-poc-vehicle-and-harness.md` already fixes the queries (`listMessages`, `listUsers`), the aggregates (A1, A2), the keying/ordering convention, and the SSE shape. Re-deriving any of this per spike would be pure waste.
- **Each sub-deliverable ships its own tests against synthetic/PoC data with no dependency on any consuming spike's code.** (Governs P7, Q8, Q9; also Success Criteria.) This is what makes both independently reviewable: a reviewer can approve either without reading 1a/1b/1c/Direction 2 code.
- **Standalone usefulness is a first-class requirement, not an incidental side effect.** (Governs P8, Q10; also Success Criteria.) Both deliverables must retain value if zero spikes are ultimately generalized to production.
- **Ground P and Q in 1c's implementation-ready design, not only in `convex_reactive`'s simpler precedent.** (Added 2026-09-12; governs P9, Q11.) 1c's KTD7-KTD9 and U4/U6 units independently designed a more advanced version of both P and Q before either existed as a shared artifact. Since 1c is not yet built, this plan targets compatibility with 1c's stricter design (generation fencing, replay ledger, JSONL schema) rather than the lighter baseline, so 1c can adopt P/Q as dependencies instead of the reverse.

### Requirements

**P — Envelope convention (atomic multi-collection write pattern)**
- P1. A single documented envelope type — `{ts, deleted, component, table, _id, _creationTime, doc}`, matching `research-skip-source-state.md`'s combined-input shape — is specified once and consumed identically regardless of which upstream spike produces envelope entries.
- P2. A reusable TypeScript library exposes: the envelope type; a per-table split-mapper helper equivalent to the shipped `ProjectsOnly`/`TasksOnly` pattern (`~/src/skip/examples/convex_reactive/skip/service.ts:34-49`); a stable keying convention (`"<component>/<table>/<id>"` or an equivalent tuple key) with a check that rejects non-unique, empty, or regenerated-per-update keys; and an order-key helper (`[_creationTime, _id]` with `_id` tiebreak) for windowed or ordered outputs.
- P3. The library documents, and enforces where feasible, the single-fork-per-atomic-unit invariant: one `writer.update(entries, isInit)` call per reassembled Transition (1a-shaped), per revision-timestamp group (1c-shaped), or per page-group swap (1b-shaped) — never N independent per-table calls for data that must appear atomically, per the hazard `DESIGN.md:114-118,314-315` names. The library documents the per-table `isInit` granularity tradeoff this single-fork invariant accepts (`research-skip-source-state.md:32-34`): bootstrap sends the full combined snapshot with `isInit: true`; steady state must send `isInit: false` deltas with explicit `[key,[]]` tombstone deletes, since a partial `isInit: true` call reads as a mass delete.
- P4. The library implements in-value revision-watermark idempotency (apply iff `entry.ts > retained_ts`) and explicitly does not reuse Skip's subscription/session-tick watermark for idempotency, per `research-skip-source-state.md`'s explicit prohibition.
- P5. The library documents the tombstone/GC policy — retain while the generation lives; wholesale discard on resnapshot/generation swap; sweep tombstone watermarks once the cursor passes the retention horizon — as a convention each consuming spike implements against, not as new runtime code this deliverable ships.
- P6. The library's split/join/order helpers are demonstrated against the frozen PoC vehicle, reproducing A1 (per-user reducer, add/remove correctness) and A2 (joined latest-N with `"Unknown"` fallback) through the envelope convention, not through spike-specific ad hoc code.
- P7. The library's own test suite exercises split, merge, ordering, watermark idempotency, and tombstone behavior directly against synthetic envelope entries, with no dependency on any spike's transport or on Q's harness — it is reviewable and testable standing alone.
- P8. The extraction states explicitly that it requires no Skip runtime or FFI change; it records the confirmed absence of a batch primitive (`research-skip-atomic-write.md`) as a still-open option for a larger future generalization, explicitly out of scope here.
- P9. The library's generation-fencing and replay-safety scope matches the stricter bar 1c's KTD7/KTD9 design already sets — a staging generation for cold/replacement builds, atomic promotion of a complete candidate, a per-page pending-ledger that withholds cursor advancement until every timestamp group in a page succeeds, and generation-scoped revision watermarks — not only `convex_reactive`'s simpler read-only pattern. Where 1c's design and `convex_reactive`'s diverge, the library follows 1c's, since 1c is the most advanced concrete consumer of this convention among the four plans (`docs/plans/2026-09-10-1854-feat-skip-data-sync-push-source-spike-plan.md`, KTD7-KTD9).

**Q — Correctness-comparator and fault-injection harness**
- Q1. A settled-checkpoint detector anchors on version timestamps (`Transition.end_version.ts`, Data Sync `UpToDate(ts)`, or an equivalent required-version marker) and exposes one "is settled" predicate reusable by any spike's driver loop.
- Q2. A dual-reader wiring compares a Skip-derived snapshot — delivered over SSE per the shape `research-poc-vehicle-and-harness.md` sketches (`POST /v1/streams/:resource`, `GET /v1/streams/:uuid`) — against an independent native Convex reader (`ConvexClient` or `convex-test`) on the same logical query, with no shared code path between the two readers. The standalone SSE endpoints bind to loopback only and serve only PoC/test-fixture data; remote listening is excluded pending a future auth model — this is a minimum-exposure constraint on the harness itself, not the "no auth model" production-hardening exclusion in Scope Boundaries.
- Q3. A normalized deep-equal comparator applies canonical sort (`[_creationTime, _id]` tiebreak, since Skip key order does not match Convex `.order().take()` order) and the tutorial's `"Unknown"`-fallback parity rule before comparing, and reports a structured mismatch (which keys/fields diverged), not a bare boolean.
- Q4. The comparator is driven against the frozen PoC vehicle: `~/src/convex-tutorial`'s `messages`/`users` tables (`convex/schema.ts:6-12`), two new unbounded app-layer queries (`listMessages`, `listUsers`), and two aggregates — A1 (per-user message count, exercising reducer add/remove) and A2 (enriched latest-N feed with join and `"Unknown"` fallback, mirroring the tutorial's forbidden `getMessages` join but computed in Skip).
- Q5. A pluggable counter/timer recorder implements `research-spike-comparison.md`'s shared catalog — delivered rows/bytes; Skip keys reconciled (added/changed/removed); dependent nodes updated; reducer add/remove; splits/rebuilds; wake-ups by cause; replays/ignored; fallbacks by reason and rate; mismatches — and the shared timer chain (`commit→readable→delivered→applied→published`, plus snapshot/reconnect/stale durations), exposing a recorder interface a spike populates without modifying the comparator itself. Per `research-spike-comparison.md`'s own per-spike metric mapping (lines 65-67), Q5's catalog is a superset: 1a is correctness-only and exempt from counters/timers "by decision," so 1a populates only Q1-Q3 and is not expected to instantiate Q5's full catalog.
- Q6. A composable fault-injection fixture implements, at minimum, the faults `research-skip-source-state.md`'s fault list marks as common to 3+ plans: disconnect-before-checkpoint; cursor expiry/invalid/ahead; table replacement plus return to snapshotting; oversized transaction; multi-table transaction in one atomic unit; `QueryFailed` vs `QueryRemoved` vs not-yet-loaded; slow-consumer/bounded-backlog exhaustion; Skip-process restart mid-CDC. Page-splits plus invalid-cursor reset (1b-specific only) is documented for reuse but not required here.
- Q7. Each fault injector exposes a "did the harness detect/recover/count correctly" assertion helper independent of which spike's source produces the fault, so a consuming spike supplies only its own trigger mechanism (e.g., how to force a disconnect) while reusing the detection/recovery assertion.
- Q8. The harness's own test suite validates its detection behavior using deliberately seeded mismatches — i.e., it proves the comparator actually catches a wrong Skip snapshot — independent of any spike's Skip integration code.
- Q9. The harness ships runnable end-to-end against the frozen PoC vehicle with a minimal reference source of its own (wiring P's envelope convention to a trivial mock, or to the existing `billf/convex/adapter` baseline) sufficient to prove Q works before any of 1a/1b/1c/Direction 2 exists to consume it.
- Q10. The report format (counts, timers, mismatch log) is directly consumable by any of the four spikes' own Success Criteria sections — a spike's report cites the harness's output schema rather than redefining metric names.
- Q11. The recorder's field names and units are the same schema as 1c's already-designed JSONL output (KTD10; `skip: examples/convex_data_sync_push/bench/compare.ts` per 1c's U6), not a separately-compatible one — 1c's harness design already exercises `research-spike-comparison.md`'s shared catalog (KTD10 explicitly states it "uses the same logical count names and units as Direction 1b where they overlap"), so Q is built by generalizing 1c's U6 design into a reusable module rather than building a generic comparator first and reconciling it with 1c's bespoke one afterward.

### How This Work Fits Together

This plan sits beneath the four spike plans in `docs/plans/README.md`, not beside them: it is a shared prerequisite tier, not a fifth spike testing its own architectural question. It builds no spike-specific transport, no backend change, and no production-facing feature. This is the current understanding, not a committed roadmap.

- **1a (`2026-09-10-1509-...`) — hard prerequisite.** Once this plan lands, 1a's R2 becomes "apply the P library's envelope convention to each reassembled `Transition`" instead of inventing its own atomic-write mechanism, and 1a's R6 becomes "adopt the Q harness's comparator and settled-checkpoint detector" instead of building a bespoke parallel-reader comparator. 1a's own Dependencies/Assumptions section (line 188) and Outstanding Questions (line 196) are the clearest textual evidence that this deferral was real, not assumed.
- **1b (`2026-09-10-1843-...`) — hard prerequisite.** 1b's R4 (atomic page-swap) consumes P directly for the page-group-swap atomic unit — its own Dependencies/Assumptions (line 193) and Outstanding Questions (line 202) state the identical undecided gap in page-swap terms; 1b's R9/R13 (settled-checkpoint comparison against a monolithic indexed query, and the scaling report) consume Q's comparator and counter/timer recorder. 1b's page-split fault (1b-specific per `research-skip-source-state.md`) is documented in Q6 for reuse but built inside 1b's own plan, not here.
- **1c (`2026-09-10-1854-...`) — beneficial reuse, not a blocking dependency.** 1c already designed its own equivalent of both P (KTD7-KTD9) and Q (`bench/compare.ts`, KTD10) before either existed as a shared artifact; 1c's R8 and R15 are already satisfied by 1c's own plan. If 1c chooses to adopt P/Q instead, P's single-fork-per-unit invariant (P3) and Q's fault-injection fixture (Q6, whose fault list 1c's R15 is the superset of) are direct fits — see Reconciliation and Recommended sequencing below for why that's worth considering, and why it is optional rather than required.
- **Direction 2 (`2026-09-10-1702-...`) — hard prerequisite for the underlying pattern, not for literal code reuse.** Direction 2's R2 (one-commit-version atomicity) and its correctness section (R13, independent-native-result comparison) name the same structural gaps P and Q fill, and Direction 2's own Dependencies/Assumptions (line 236) and Outstanding Questions (line 247) state the identical undecided design question 1a and 1b state — that is what makes this a hard prerequisite for Direction 2 too. But Direction 2 is backend-owned (its own plan explicitly rejects an "external change-feed sidecar" to avoid entangling it with Direction 1), while P is an external TypeScript library over Skip's `writer.update`/`CollectionWriter` adapter surface and Q's dual-reader is hard-coded to that same external SSE resource. Direction 2 cannot import P or wire into Q as built; it would need a distinct backend-native atomic-write pattern and a native-Convex-client-based comparator reader, applying the same combined-collection *insight* P documents, implemented natively rather than as an external library. Direction 2's R12 (mismatch metrics) and R15 (scaling report) can still cite Q5's shared counter catalog as a naming convention, independent of the transport mismatch above.
- **`docs/plans/README.md`** — This plan is the missing "Evidence hierarchy" layer beneath the four spikes' shared correctness bar (README's "Shared constraints" section) and above the raw Phase 1 research. The README's per-spike gap table already flags `research-spike-comparison.md`'s per-spike metric mapping as resolved (lines 60-82 of that research doc); this plan is what turns that mapping into runnable code (Q5) rather than leaving it as a citation gap. README should be updated, as a follow-up outside this plan's scope, to list this plan as a prerequisite tier above the four spikes once it exists.

**Research beneficial to every plan, including 1c — separate from the P/Q hard/beneficial split above.** Some of the research grounding this plan draws on was already valuable to all four spikes before P and Q existed as deliverables, and remains so regardless of who ends up building or adopting P/Q: `research-poc-vehicle-and-harness.md` freezes the shared PoC vehicle (`~/src/convex-tutorial`'s `messages`/`users` tables, the `listMessages`/`listUsers` additions, and the A1/A2 aggregates) that every sibling plan's own Sources/Research section already points to, 1c's included. `research-spike-comparison.md`'s N/K/F scaling axes and shared counter/timer catalog give all four plans a common vocabulary for reporting scaling results, independent of whether a given spike's own harness is Q or something bespoke — 1c's KTD10 explicitly aligns its own JSONL schema to this catalog's naming without needing to consume Q's code, and Direction 2's backend-native comparator (which cannot consume Q as built — see the Direction 2 bullet above) can cite the same catalog by name for the same reason. `research-skip-atomic-write.md` and `research-skip-source-state.md` document the underlying atomic-write options and the envelope/tombstone/watermark conventions that all four plans' own Sources sections cite; this plan's Problem Frame verification against them is what closes 1c's own flagged "Deferred / Open Question" about whether Skip's `ExternalService` actually supports the primitives KTD7-KTD8 assume (see Reconciliation below) — a benefit to 1c even though 1c wrote its own implementation rather than adopting P wholesale.

**Reconciliation with 1c's implementation-ready detail (added 2026-09-12).** 1c's plan was independently deepened to `implementation-ready` on 2026-09-11 — the same day this plan was first drafted — without either plan consuming the other. The result is the exact duplication this plan's Problem Frame predicted, now concrete rather than hypothetical: 1c's KTD7-KTD9 and its U4 implementation unit (`skip: skipruntime-ts/adapters/convex/src/data_sync_push.ts`) design a full generation-fenced, replay-safe combined-collection scheme from scratch, and its U5-U6 (`convex-tutorial: convex/chat.ts`; `skip: examples/convex_data_sync_push/bench/compare.ts`) design a complete deterministic-mutation oracle and comparison harness from scratch — both are exactly P and Q, independently re-derived. Because 1c's plan is implementation-ready but **not yet built** (the 2026-09-11 commit touched only the plan document, no code), this is the last point where reconciliation is cheap: after U4/U6 land, unwinding a bespoke implementation back onto a shared library costs a rewrite; before they land, 1c can simply consume P and Q as its U4 and U6 dependencies.

Two changes follow from this, both applied to this plan's Requirements below:
1. **P's bar is raised to match 1c's stricter design, not just `convex_reactive`'s simpler one.** `convex_reactive` proves the single-combined-collection *write* pattern works, but has no generation fencing, no replay ledger, and no revision watermarks — it doesn't need them for a read-only demo. 1c's KTD7/KTD9 do need them, and 1c's own design is the most advanced concrete requirement any of the four plans carries. P is scoped to meet 1c's bar (new P9 below), not the lighter one.
2. **1c's own plan flags exactly the risk P's research already resolves.** 1c's "Deferred / Open Questions" section (added in the same 2026-09-11 revision) lists, at confidence 75: "Skip `ExternalService` support for generation-fenced staging and one atomic multi-table update is unverified against Skip's source... KTD7's generation-fenced state machine and KTD8's one-`callbacks.update`-call design... assume specific `ExternalService` capabilities [that are not confirmed]... Confirm before U4 architecture is finalized." **Benefits beyond strict prerequisite status.** Two things become possible only once this plan exists, beyond simply unblocking each spike's own R-numbered requirement: (1) the shared metric catalog `research-spike-comparison.md` defines stops being a citation-only alignment document and becomes literal shared code (Q5) that every spike's report can cite verbatim, making the four spikes' scaling claims genuinely comparable rather than independently-worded approximations of the same vocabulary; (2) the fault-injection fixture (Q6) turns eight-plus independently-described fault scenarios spread across three plans into one tested, reusable set of assertion helpers, so a bug found in the detection logic for, say, cursor-expiry handling gets fixed once for every spike that exercises it, instead of three times.

**Is this independently reviewable?** Yes, on two separate, concrete grounds. The P library's interface boundary is: input (an envelope-shaped entry stream), output (split-per-table Skip collections, ordered views, correctly deduplicated writes), and its own test suite (P7) exercised against synthetic entries with no reference to any spike's transport. A reviewer can approve the P library PR's correctness of implementation by reading its type definitions, its README describing the envelope convention, and its test suite — nothing else. Judging whether P9's generation-fencing scope is the *right* scope is a separate question from implementation correctness, and does require reading 1c's KTD7-KTD9 (`docs/plans/2026-09-10-1854-feat-skip-data-sync-push-source-spike-plan.md`) — P9's scope-justification review is not self-contained the way P1-P8's is. The Q harness's interface boundary is: input (a settled-checkpoint signal plus two data sources — one Skip, one native Convex), output (a pass/fail plus structured mismatch report, a populated counter/timer object, and fault-detection assertions), and its own test suite (Q8) exercised against deliberately seeded mismatches with no reference to any spike's Skip integration. A reviewer can approve the Q harness PR by reading its comparator logic, its fault injectors, and its seeded-mismatch tests — again, nothing else. Neither deliverable's review requires understanding 1a's WebSocket client, 1b's page topology, 1c's Data Sync stream, or Direction 2's backend-native execution model.

**Is this useful standalone?** Yes, independent of whether any spike is ultimately generalized to production. The P library is a reusable Skip/Convex integration pattern with a proven shipped precedent (`~/src/skip/examples/convex_reactive`) and is a plausible candidate for direct upstream contribution to `~/src/skip` itself — it documents a real solution to a gap in Skip's public API (the missing batch-write primitive) that any Skip/Convex integration, not just these four spikes, will eventually hit. The Q harness is, today, the only concrete correctness-oracle artifact any of the four spikes has; `research-poc-vehicle-and-harness.md` states no harness exists anywhere in this codebase. Building it de-risks evaluation of all four directions regardless of which one (if any) is chosen, because it is the thing that turns "Skip looks right" into a checked claim rather than an eyeballed one — that value exists whether the eventual answer is "generalize 1c," "generalize none of them," or something not yet conceived.

### Key Flows

- F1. Envelope round-trip through the P library
  - **Trigger:** A2's reference wiring (A4) sends a batch of tagged envelope entries spanning both `messages` and `users`.
  - **Actors:** A2, A6.
  - **Steps:** The library validates keys and order metadata, issues one `writer.update(entries, isInit)` call, and Skip's mappers split the batch into per-table collections and reduce A1's per-user count.
  - **Outcome:** Both tables' contributions land in Skip from a single atomic write; no intermediate state where one table has advanced without the other is observable.
  - **Covers:** P1, P2, P3, P6.
- F2. Atomic multi-table transaction through P
  - **Trigger:** A minimal reference mutation touches both `messages` and `users` in one Convex transaction.
  - **Actors:** A1, A2, A6.
  - **Steps:** The reference source (A4) packages both tables' changes for that transaction into one envelope batch tagged with the same `ts`, and issues one `update` call.
  - **Outcome:** A1's reducer and A2's join both observe the change as one atomic step, satisfying the same atomicity shape 1a's R2, 1b's R4, 1c's R8, and Direction 2's R2 each independently require.
  - **Covers:** P3, P4.
- F3. Comparator settled-checkpoint match
  - **Trigger:** A write is driven through the PoC vehicle app.
  - **Actors:** A1, A3, A6.
  - **Steps:** Q's settled-checkpoint detector (Q1) waits for the write to settle, snapshots A6's Skip-side SSE resource, independently re-reads A1 via `ConvexClient`/`convex-test`, normalizes both (Q3), and compares.
  - **Outcome:** A pass records a match; a mismatch produces a structured report identifying the diverging keys/fields, not a bare failure.
  - **Covers:** Q1, Q2, Q3, Q4.
- F4. Fault injection detection
  - **Trigger:** A fault injector (e.g. forced disconnect, cursor expiry, Skip-process restart) fires mid-flow.
  - **Actors:** A3, A4, A6.
  - **Steps:** The injector triggers the fault; the harness asserts that the fault is detected, that recovery reaches a matching state at the next settled checkpoint, and that the fault is counted under the correct catalog entry.
  - **Outcome:** The fault's detection/recovery/counting behavior is proven once, reusable by any spike that later wires its own trigger mechanism into the same assertion helper.
  - **Covers:** Q6, Q7.
- F5. Harness self-validation (no spike present)
  - **Trigger:** Q's own test suite runs against the minimal reference source (A4) with a deliberately seeded mismatch.
  - **Actors:** A3, A4.
  - **Steps:** The comparator runs against the seeded-wrong Skip snapshot and the correct native result.
  - **Outcome:** The comparator reports a mismatch, proving it actually catches divergence rather than trivially passing.
  - **Covers:** Q8, Q9.

### Alternatives Considered

- **Let each spike build its own atomic-write shim and comparator independently.** This is the status quo the four plans currently defer to. Rejected: it is the exact duplication this plan exists to remove — four independent re-derivations of the same envelope convention and four independent, untested comparator implementations, with no shared correctness oracle and no shared metric vocabulary in practice (only in research-doc alignment).
- **Wait for a Skip runtime `updateMany`/batch primitive before building anything.** Rejected: no evidence this is imminent (absent through the CHANGELOG history, no relevant git history per `research-skip-atomic-write.md`), and a proven, shipped workaround already exists and does not require it.
- **One combined plan document with a single unified requirement list, no P/Q split.** Rejected: this would obscure that the two deliverables have different plausible implementers and independently reviewable interface boundaries, and would make partial progress (e.g. P done, Q not yet) illegible against a single requirement numbering.
- **Two fully separate plan documents, one per sub-deliverable.** Rejected: they share the same frozen PoC vehicle and the same relationship to all four downstream spikes; splitting would duplicate the vehicle-freezing content and the work-relationships mapping, and would obscure that both must land before any spike can be implemented and evaluated for real.
- **Build the harness against a synthetic vehicle instead of `~/src/convex-tutorial`.** Rejected: `research-poc-vehicle-and-harness.md` already froze convex-tutorial as the shared vehicle, citing its use by Direction 2 and pointing 1a/1b/1c readers to the same source; diverging would break the "one shared vehicle" goal this plan depends on.
- **Build P/Q incrementally inside the first spike attempted, and generalize afterward, instead of fully upfront and blocking.** Rejected for this plan's scope: the four sibling plans already independently re-derived the same two gaps in their own planning text (see Problem Frame), which is itself evidence the shape generalizes; building upfront also gives every spike the same correctness oracle from day one rather than staggering it. Accepted tradeoff: this serializes all four spikes' real implementation behind this plan's completion rather than letting the first one start immediately.
